##### 问题五：**关于领域 Embedding 调优：** 通用的 Embedding 模型（如 BGE 或 OpenAI）可能不理解‘提速包’和‘叠加包’在计费上的本质区别。**你是否对 Embedding 模型做过微调？如果没有，你通过什么样的‘硬对齐’（如词表加权或特征工程）来弥补向量模型对联通专有业务术语理解的不足？**
在通信这种强领域语义场景下，通用 Embedding 确实容易把“提速包”和“叠加包”这类业务概念混淆。
在我的项目中，我们没有优先做 Embedding 微调，而是采用了一套“硬对齐”的工程策略来弥补通用模型的领域理解不足。
第一，在 Query 侧构建业务术语词典，对关键业务词做语义扩展。例如把“提速包”重写为“临时提升带宽速率的业务”，再送入 Embedding，这样可以在向量空间中拉开不同业务类型的距离。
第二，在文档侧注入结构化特征，例如增加“业务类型=提速类”或“计费逻辑=流量叠加”等标签，并参与向量化，形成业务语义聚类。
第三，在召回阶段增加业务标签过滤，对向量 TopK 结果做一次语义后验校正，避免提速类问题召回到流量叠加类文档。
通过这三层硬对齐策略，在不做模型微调的情况下，也能显著降低业务语义混淆问题，满足客服场景的准确率要求。
**如果是通用知识库、数据量较小，或者业务更新非常频繁的场景，通常不会优先选择微调，而是通过词典对齐、查询重写、结构化特征注入等工程手段来解决语义问题。**
