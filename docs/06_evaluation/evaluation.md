#### 问题一 你之前提到的 94% 的准确率，你是怎么测出来的？你是否构建了一个 **Ground Truth (标准答案集)**？是用代码自动跑批（Batch Testing）对比模型输出结果，还是人工抽检？

94% 的准确率不是基于主观评估，而是基于一个有 Ground Truth 的结构化评测集。
1、线上真实对话日志
2、人工构造的覆盖集
3、异常样本，包括用户投诉工单，历史失败记录
虽然输入是自然对话，但每条样本都预先标注了业务意图、期望调用的 tool 和标准参数。模型在一次生成中只要 tool 或参数有任何偏差，就判失败。  
同时我们也单独关注意图覆盖率和回答是否覆盖用户问题，这些通过槽位校验和规则化判断来验证。离线评测主要用于版本对比，最终以线上 tool 成功率和人工兜底率作为闭环验证。



##### 问题二：从 85% 到 94% 这最难的 9 个百分点提升里，**最大的一个 Bad Case 类别是什么？** 最终是靠改切分算法解决的，还是靠增加图谱关联解决的？

**回答：** 85%到94%的提升最大的bad case，不是模型不行，而是语义证据被切分算法物理隔离了，我们首先通过父节点策略，绑定到同一个chunk内，绑定后，我们没有直接检索超大 Chunk，而是采用了 子块嵌入（Embedding）指向父块内容（Full Content）的模式。向量库里存的是切分细致的规则条目，但当该条目被命中后，系统会强制将其父节点下的所有关联约束（如同级条款、表格解释说明）一并作为 Context 输入给大模型。其次，我们通过将逻辑上强绑定的条款强制放在同一个chunk内。最后，我们针对表格与解释条款可能会存在不关联的情况，我们通过改进，当遇到表格时，自动扫描前后文档，直至不在同一个标题内，将所有标注、补充说明与表格ID绑定，打上相关的group_id的元数据。




##### 问题三：剩下那 6% 的 Bad Case 你们分析过吗？是什么原因导致的？是目前的 RAG 架构无法解决的吗？既然知识图谱的贡献只有1-2%，且维护成本高，为什么还有保留？

**回答：** 剩下的 6% 主要集中在**模糊语义和隐性推理**。比如用户问‘有没有性价比最高的方案’，‘性价比’是一个主观且需要全量对比的词，RAG 很难通过局部召回给出完美答案。这部分我们目前在尝试通过 **Agent 的多轮对话引导**，让用户提供更具体的约束（如具体的通话分钟数需求）来解决。对知识图谱的坚持时因为业务套餐规则经常会变换，图谱提供了一种热更新的方式，其次时在账务系统中，1-2%的case往往是致命的，准确性比效率更重要，尽管提升1-2%,但是也是不可或缺的。




##### 问题四：94% 是在多大的测试集上跑出来的？你的 Golden Dataset（金标准数据集） 是如何构建的？是完全人工标注，还是利用 LLM 辅助构造（如反向生成指令）？针对联通那种‘换个说法意思全变’的业务套餐，你如何确保测试集覆盖了语义边界（Edge Cases），而不是只测了容易召回的简单 Query？

**回答：** 94%成功率是在一个大约9k规模的 Golden Dataset 上评估得到的，这个数据集不是纯人工或纯LLM生成，而是三源融合构建的。
大约60%来自人工标注的真实客服对话，保证数据真实性；20%到30%通过LLM生成语义扰动样本，扩充表达多样性；另外10%到20%来自线上失败样本回流，用于覆盖真实业务问题。
通信业务中“换个说法意思全变”的场景，我们专门设计了语义边界样本，例如取消、变更、咨询等极易混淆的表达对，并将线上失败样本持续注入测试集。
在评估时，我们还按难度分层统计准确率，确保94%的结果不是只在简单样本上取得的，而是在包含Edge Case的完整数据分布下得到的。





##### 问题五： 这 2 万条数据是如何保证覆盖了联通成千上万种套餐组合的边缘情况（Edge Cases）的？你是如何量化你的训练集‘多样性’的？你是否利用了语义聚类（Clustering）或者数据指纹来剔除冗余数据，防止模型在某些高频套餐上过拟合而在长尾业务上‘遗忘’？

| 维度   | 示例取值                  |
| ---- | --------------------- |
| 套餐类型 | 主套餐 / 叠加包 / 提速包 / 日租包 |
| 资源类型 | 流量 / 通话 / 短信 / 带宽     |
| 生效方式 | 立即生效 / 次月生效           |
| 有效期  | 日包 / 月包 / 年包          |
| 限速策略 | 不限速 / 达量限速 / 封顶       |
| 用户类型 | 新用户 / 老用户 / 校园用户      |
我们并不是通过穷举所有套餐组合来构建这2万条训练数据，而是先把通信套餐抽象为几个核心语义维度，例如套餐类型、资源类型、生效方式、有效期和限速策略等。  
然后基于这些语义维度做组合采样，保证每种语义模式都有一定数量的问法，从而用2万条数据覆盖上千种实际业务组合。

在多样性量化方面，我们主要做了三件事。  
第一，对所有query做embedding后进行语义聚类，观察不同语义簇的分布，并通过簇分布熵来评估数据是否过度集中在少数高频业务上。  
第二，定义核心业务意图集合，统计训练集的intent覆盖率，确保关键业务语义都有样本。  
第三，利用embedding指纹做近似去重，去除相似度过高的重复问法，防止模型在高频套餐表达上过拟合。

同时在采样策略上，我们采用分层采样，对长尾业务进行重加权，并结合困难负样本挖掘，让模型学习容易混淆的业务边界，从而避免在主流套餐上表现很好，但在长尾业务上出现语义遗忘的问题。
