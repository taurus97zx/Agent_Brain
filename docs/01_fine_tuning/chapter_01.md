##### 问题二：多轮推理链样本
- **深挖点：** 在 SFT 时，你的数据格式是 **ReAct 格式**（Thought-Action-Observation-Thought-Final Answer），还是纯粹的 **Input-Output JSON**？
- **难点：** 账务逻辑往往涉及：查余额 -> 查套餐 -> 计算差额。如果模型在中间某一步（Thought）推理错了，但最终凑巧输出了正确的 JSON 格式，你会如何处理这种“伪正确”的训练样本？你如何保证模型在微调后，依然具备足够的**逻辑鲁棒性**，而不是仅仅学会了填 JSON 模版？


回答：在真实的企业级的训练场景中，训练的数据是这样的：
```
{
  "intent": "QUERY_BILL",
  "steps": [
    {"action": "QUERY_BALANCE", "tool_required": true},
    {"action": "QUERY_PACKAGE", "tool_required": true},
    {"action": "CALCULATE_DIFF", "tool_required": false}
  ],
  "final_action": "RETURN_RESULT"
}
```
在政企账务 SFT 中，我们**不会直接使用完整 ReAct（Thought-Action-Observation-Thought-Final）格式进行训练**，也**不会只做“Input → Output JSON” 的黑盒映射**。  
实际采用的是一种 **“隐式推理对齐（Hidden Reasoning Alignment）+ 显式中间状态校验（Observable State Validation）”** 的混合策略：
- **训练时不暴露 Thought**
- **但通过可验证的中间结构，强制约束模型的推理路径**  
    从而避免“伪正确样本”污染模型。
模型在系统中不输出数值，模型不进行计算、模型只声明要做那几步。


**负样本问题：**
训练样本都必须通过步骤可达性与一致性校验，任何“结果正确但路径错误”的样本都会被视为负样本丢弃或反向训练，从而保证模型学到的是稳健的业务因果结构，而不是 JSON 模板复读。
```
{
  "input": "账单和套餐差额是多少",
  "output": {
    "intent": "BILL_DIFF_QUERY",
    "plan": ["CALCULATE_DIFF"],
    "error": "MISSING_DEPENDENCY",
    "must_not_answer": true
  }
}
```

##### 问题八：你引入了知识图谱，这属于典型的 GraphRAG 模式。请问图谱在这里是用于**检索前的查询扩展（Query Expansion）**，还是用于**检索时的路径导航**，或者是**结果生成时的约束校验**？
**回答：** 知识图谱最重要的作用是在检索的时候，进行路径导航，明确哪些路径“合法”，哪些路径“根本不该被走”。Graph 先裁剪“规则空间”，  Text RAG 只是在这个空间里找证据。第二作用是进行结果生成的约束，具有一票否决权，prompt是软约束，Graph是硬约束。查询扩展是最不重要的，因为扩展会查出多个相关的，而不是必须成立的，引入了干扰，会导致召回率下降。


##### 问题九：从 85% 到 94% 这最难的 9 个百分点提升里，**最大的一个 Bad Case 类别是什么？** 最终是靠改切分算法解决的，还是靠增加图谱关联解决的？

**回答：** 85%到94%的提升最大的bad case，不是模型不行，而是语义证据被切分算法物理隔离了，我们首先通过父节点策略，绑定到同一个chunk内，绑定后，我们没有直接检索超大 Chunk，而是采用了 子块嵌入（Embedding）指向父块内容（Full Content）的模式。向量库里存的是切分细致的规则条目，但当该条目被命中后，系统会强制将其父节点下的所有关联约束（如同级条款、表格解释说明）一并作为 Context 输入给大模型。其次，我们通过将逻辑上强绑定的条款强制放在同一个chunk内。最后，我们针对表格与解释条款可能会存在不关联的情况，我们通过改进，当遇到表格时，自动扫描前后文档，直至不在同一个标题内，将所有标注、补充说明与表格ID绑定，打上相关的group_id的元数据。




##### 问题十：剩下那 6% 的 Bad Case 你们分析过吗？是什么原因导致的？是目前的 RAG 架构无法解决的吗？既然知识图谱的贡献只有1-2%，且维护成本高，为什么还有保留？

**回答：** 剩下的 6% 主要集中在**模糊语义和隐性推理**。比如用户问‘有没有性价比最高的方案’，‘性价比’是一个主观且需要全量对比的词，RAG 很难通过局部召回给出完美答案。这部分我们目前在尝试通过 **Agent 的多轮对话引导**，让用户提供更具体的约束（如具体的通话分钟数需求）来解决。对知识图谱的坚持时因为业务套餐规则经常会变换，图谱提供了一种热更新的方式，其次时在账务系统中，1-2%的case往往是致命的，准确性比效率更重要，尽管提升1-2%,但是也是不可或缺的。





##### 问题十一：你提到的2万条高质量对话指令数据是如何构建的？是基于业务日志清洗、人工编写，还是通过大模型（如GPT-4）蒸馏生成的？如果是混合的，比例大概是多少？”在构建数据时，你是如何定义‘高质量’标准的？针对业务场景（比如联通政企套餐），你设计了哪些具体的Prompt Template（提示词模板）来规范数据格式？

回答：关于这2万条微调数据，我们采用的是**‘业务真实数据 + 合成数据 + 专家精调’的混合构建策略**，旨在平衡模型的业务落地能力与泛化鲁棒性。具体构成比例大约是 **3:3:3:1**，具体如下：
- **30% 历史客服对话**： 这部分数据包含用户真实的口语表达、噪音和习惯用语。引入这部分数据是为了让模型‘接地气’，适应真实业务场景中的非标准提问
- **30% 大模型生成的边界场景**：真实数据往往集中在长尾的头部（常见问题），缺乏极端情况。我们专门生成了针对**业务边界、恶意攻击、或逻辑冲突**的场景（比如用户同时办理互斥套餐），以此提升模型的安全性和逻辑判断能力。
- **30% 通用指令数据**：增强模型对‘指令（Instruction）’本身的理解能力，确保模型不只是在‘聊天’，而是在‘执行任务’。
- **10% 人工专家标注**：用于解决最复杂、最核心的业务逻辑，作为微调的‘核心锚点’，确保关键业务零失误
数据质量方面我们也进行了去重处理,通过语义相似性，防止模型死记硬背，去除手机号，身份证等敏感信息，进行一致性校验，剔除答非所问的样本。

#### 问题十三：在利用大模型进行三元组抽取（S-P-O）。但在实际运行中，大模型输出的 JSON 经常会出现**格式错误（如少个括号）**或者**属性名不统一（如有时叫‘金额’，有时叫‘月费’）**。针对这两个问题，你在代码层面和 Prompt 层面分别做了哪些‘保底’措施？

**第一层收敛：** predicate 只能从固定集合中选择，不允许自创字段。

#### 问题十四： 业务套餐名称往往包含嵌套关系，比如‘5G北向流量包’。你如何确保模型不会把它拆成‘5G’和‘流量包’两个独立的实体？在标注这 2 万条数据时，你是如何定义这种复合实体的边界规范的？


我们进行业务词典约束 + 抽取阶段约束（few-shot） + 后处理回收机制（匹配合并），如果有独立的产品编码，则视为完整的实体，比如5G北向流量包，通过维护一个”强实体的词典“，用作实体边界校验和冲突裁决的标准源。

**实体边界校验和冲突裁决的标准源：** 指的是当模型将语义拆分为了5G、北向流量包两个时，以业务库中的语义为准，进行边界修正和冲突消解。
