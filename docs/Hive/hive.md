#### 问题二：在Hive中，如果你直接对几亿条数据使用 Order By，会有什么后果？**Sort By、Distribute By 和 Cluster By 有什么区别？** 在联通这个场景下，你会如何组合使用它们来既保证有序又不撑爆集群？


在Hive中，ORDER BY 是全局排序，会强制所有数据进入一个Reducer。如果对几亿甚至PB级数据使用 ORDER BY，会导致单节点排序瓶颈，严重时会出现内存溢出或任务失败。

**错误写法：**
```
INSERT OVERWRITE TABLE dwd_ticket
SELECT *
FROM ods_ticket
ORDER BY create_time;
```

**正确写法：**
```
SET mapreduce.job.reduces=256;

INSERT OVERWRITE TABLE dwd_ticket
PARTITION (dt)
SELECT
    ticket_id,
    user_id,
    complaint_text,
    create_time,
    dt
FROM ods_ticket
DISTRIBUTE BY dt, hash(ticket_id)
SORT BY dt, create_time;
```

**执行步骤：**
```
dt=2026-02-01 → Reducer1
dt=2026-02-02 → Reducer2
dt=2026-02-03 → Reducer3
```



#### 问题三： 当后端规则库更新时，**你如何保证向量数据库的‘读写一致性’？** 你在索引重建期间是如何做‘平滑过渡’的，以防用户在 12:00 重建索引时查到 11:59 的过期资费？

我们在资费这类强一致性场景中，采用“主库权威 + 双索引版本 + 原子切换 + 增量同步”的方案来保证读写一致性。
第一，向量库只负责语义召回，不直接作为资费的最终数据源。在生成答案前，我们会根据召回到的套餐实体，实时查询业务主库做二次校验，确保价格始终来自最新规则。
第二，在索引重建时，我们采用双版本索引策略。例如线上使用 index_v1 服务，同时后台构建 index_v2。构建完成后，通过 alias 做原子切换，整个过程对用户无感知，也不会出现半新半旧的数据。
第三，日常资费变更采用 CDC 增量索引机制，只更新受影响的文档，通常可以在几十秒内同步到向量库，避免整库重建带来的不一致窗口。

因此，即使在12:00资费更新、12:00–12:02索引重建期间，系统仍然通过“旧索引召回 + 主库实时校验”的方式保证用户查到的是最新资费，实现平滑过渡。




**知识点一：** 月初一号，联通总部的数据分析师在 Hue（大数据查询界面）上敲下了一段 SQL，统计**“昨日各省份通过微信渠道缴费的总金额**

```
SELECT province, SUM(pay_amount) 
FROM unicom_payment_log 
WHERE dt = '2026-02-25' AND pay_channel = 'WeChat' 
GROUP BY province;
```

**后台并没有一个真正的关系型数据库在跑**
1. **解析器（Parser）**：检查小李写的 SQL 语法对不对，有没有拼写错误，生成抽象语法树（AST）。
2. **编译器（Compiler）与元数据（Metastore）**：Hive 去 MySQL（通常作为 Metastore）里查一下：unicom_payment_log 这个表存在吗？province 字段有吗？它存在 HDFS 的哪个目录下？
3. **优化器（Optimizer）**：Hive 发现有 WHERE dt = '2026-02-25'，它会做一个极其重要的动作——**谓词下推（Partition Pruning，分区裁剪）**，告诉底层引擎：“别扫全表，只去 2026-02-25 那个文件夹底下读数据”。
4. **执行器（Execution）**：Hive 将优化后的逻辑转化为 **MapReduce（或 Tez/Spark）任务**，提交给 YARN 集群：
    - **Map 阶段**：几千台联通服务器同时去读自己磁盘上的缴费日志文件，过滤出微信支付的记录，并提取出 [province, pay_amount] 作为键值对。
    - **Shuffle 阶段**：根据省份（province）进行网络分发，比如所有把“广东”的数据发给 Reducer A，“北京”的数据发给 Reducer B。
    - **Reduce 阶段**：Reducer A 将收到的广东所有金额累加（SUM），输出最终结果写回 HDFS。


**知识点二：** 表设计：内部表 vs 外部表

- **外部表（External Table）：存储原始流水数据（ODS层）**
    - **设计**：网关每天会把海量的原始缴费日志推送到 HDFS 的 /data/unicom/raw_payment/ 目录下。我们在 Hive 建一张**外部表**指向这个目录。
    - **特点**：Hive 只负责“读取”它的结构（Meta信息）。如果有一天某位新手运维不小心执行了 DROP TABLE raw_payment;，**只会删掉表结构，HDFS 上的真实日志文件依然安然无恙**
    - **应用场景**：这非常重要，因为这些原始文件可能不仅 Hive 要用，联通的安全风控系统（比如用 Flink 做实时反欺诈）也要读同一份文件，数据的所有权不能归 Hive 独占。
- **内部表（Managed Table）：存储加工后的汇总数据（DWS/ADS层）**
    - **设计**：大数据工程师每天半夜跑定时任务，把外部表里的明细清洗、汇总，算出“每个用户每日总缴费表”，存入**内部表** user_daily_bill。
    - **特点**：这张表是 Hive 自己生成的，完全由 Hive 管理。如果执行 DROP TABLE user_daily_bill;，**表结构和 HDFS 上的数据文件会被一起物理删除**。
    - **应用场景**：适合存放中间计算结果或最终报表数据。


**知识点三：** 表设计：分区表（Partition）与分桶表（Bucket）
**【分区表（Partition）—— 宏观隔离，减少数据扫描量】**
- **概念**：在 HDFS 上以**文件夹**的形式对数据进行物理隔离。
- **业务场景**：联通全国有几亿用户，一年的缴费记录高达数百亿条。如果不分区，查一天的账要把一年的数据全扫一遍（全表扫描）。
- **设计**：按**日期（dt）**和**省份（province）**进行双重分区。
    - HDFS 目录结构会变成这样：  
        /unicom/payment/dt=2026-02-25/province=BJ/  
        /unicom/payment/dt=2026-02-25/province=GD/    
- **使用场景**：当客服系统查询“2月25日北京地区缴费异常”时，Hive 直接定位到对应子目录，扫描数据量从 TB 级瞬间降到 GB 级。
    

**【分桶表（Bucket）—— 微观打散，优化 Join 和采样】**
- **概念**：在分区的基础上，对某个字段（如 user_id）进行 Hash 计算，将数据分散到多个**文件（File）**中。
- **业务场景**：每到月底，联通需要出账单，需要把**“庞大的用户基础信息表（包含数亿人）”**和**“庞大的当月缴费明细表（包含数十亿流水）”**进行 JOIN 操作。两个百G大表直接 Join 会卡死。
- **设计**：将这两张表都根据 user_id 分为 256 个桶（Bucket）。
    - 原理：因为 Hash 算法相同，同一个 user_id（比如张三的号码）在两张表里，**必定都会落入各自的第 N 个桶（文件）中**。
- **使用场景**：此时两表 Join（SMB Join），就不需要全网跨节点大洗牌（Shuffle）了，只需把第一张表的第 1 个文件，和第二张表的第 1 个文件直接在本地合并即可，性能呈指数级提升。


**知识点四：** 联通在搞“双11充100送50”活动。第二天大数据平台在跑全国渠道充值业绩统计（GROUP BY pay_channel）。  
集群里分配了 100 个 Reducer 执行任务。你在监控大屏上看到：99个 Reducer 都在 10 秒内跑到了 100%，唯独**第 78 号 Reducer 卡在 99% 长达几个小时出不来**。集群资源被耗尽，甚至最终抛出 OOM（内存溢出）报错。

在 Shuffle 阶段，系统是按 Key 分发数据的。而在联通的实际业务中，**“微信支付”和“支付宝”可能占了总缴费笔数的 90%**，而其它“营业厅现金”、“某小众银行APP”只有 10%。  
结果就是处理“微信支付”这个 Key 的那一个 Reducer 节点，被塞入了数亿条数据，当场累死；而处理小渠道的节点瞬间秒完在那闲着。这就是**数据倾斜**。


- **思路 1：参数干预（最简单，第一道防线）**
    - 设置 set hive.groupby.skewindata=true;。
    - **原理**：Hive 底层会把一个 MapReduce 拆成两个。第一个 MR 强行把微信的数亿条数据随机加上随机数打散，分给多个 Reducer 先做一波局部求和（比如算出几百个局部的微信流水汇总）；第二个 MR 再把这些局部结果汇总成最终的微信总额。这叫**两阶段聚合**。
- **思路 2：MapJoin（适用于大小表关联导致倾斜）**
    - **场景**：如果是缴费明细表（几十亿条）去 Join 渠道信息维度表（只有几十条，如渠道ID和渠道名称对应表）。
    - **解决**：使用 MapJoin（set hive.auto.convert.join = true;）。
    - **原理**：直接把只有几十条的小表加载到各个 Map 节点的内存里，在读取巨型流水表的 Map 阶段直接完成 Join，**完全跳过 Shuffle 阶段**。没有 Shuffle，就不存在按 Key 分配不均，直接根除了倾斜。
- **思路 3：手动加盐打散（Salting，高端局必备）**
    - **场景**：大表 Join 大表，且某个 user_id 是超级大客户（比如一个企业代缴账户，一天产生几十万笔流水）。
    - **解决**：在写 SQL 时，人为地在这个超大客户的 user_id 后面加上 _0 到 _9 的随机后缀。让原本去往同一个节点的巨量流水，分散到 10 个节点去关联，最后再去一次后缀求和。
